# Онбординг агента в репозиторий

Цель: через один проход понять, **как здесь работать**, не переписывая продукт.

**Вход.** Корень текущего репозитория. **Выход.** Карта: стек, overlay, контракты, как проверяют и выкатывают, дыры, первый безопасный шаг. **Запреты.** Читать значения секретов; менять стек; «генеральная уборка»; копировать секреты в чат или другой репозиторий; фиксировать ограничение среды или продукта без эмпирической проверки — отсутствие наблюдения не есть наблюдение отсутствия: ограничение записывается вместе с командой, которой проверено; сбой инструмента — свойство среды, не продукта. **Evidence.** Факты из файлов (lockfile, README, ADR), не догадка. **Стоп.** Нет, кроме секрета в git — тогда Blocker этой находки. **Дальше.** Поручение → `autoteam-orchestrator` или роль из каталога.

## Порядок

1. Корень: README, `docs/CURRENT.md` или аналог, `docs/process/` если есть.
2. Стек по факту (lockfile, манифест, compose, ADR). Зафиксируй факт. Нет стека — в карте «стек не задан», не назначай язык. Правило: канон метода `docs/process/stack.md`.
3. Overlay агентной среды: конфиг-каталоги в корне (`.claude/`, `.cursor/`, `CLAUDE.md`, `AGENTS.md` и аналоги), свой `docs/process/model-routing.md`.
3а. Копия канона autoteam в продукте — кэш: при доступном каноне обнови её целиком при старте цикла (перезапиши, не сверяй по кусочкам), зафиксируй в handoff. У канона есть удалённый источник (git remote) и есть сеть — сначала обнови сам канон (`git pull`), потом копируй. Версия канона (тег/коммит), на которой стартовал цикл, — в бриф; посреди цикла канон не обновляется. Канон недоступен — работай по копии. Работать по устаревшей копии при доступном каноне — ошибка.
3б. Какие ещё агентные среды работают в этой папке (конфиг-каталоги, свежие чужие правки) — в карту как риск: одновременная работа двух сред в одной рабочей папке — инцидент периметра, не фон.
4. Секреты: знай путь (`secrets/`, `.env.example`), **не** выводи значения, не коммить.
4а. Инвентаризация ресурсов: какие учётки, доступы, среды и данные у продукта уже есть (по `.env.example`, deploy, runbook, docs — не читая значений) → реестр `docs/process/resources.md` продукта, шаблон `templates/resources.md` канона.
5. Контракты: OpenAPI / AsyncAPI / SQL init / protobuf — что есть.
5а. Спецификации предметной области и алгоритмов (docs, ADR, документы, на которые ссылаются комментарии кода) — в карту как источник правды. Явная ссылка из кода на документ — обязательное ребро: видел — открой; не открыл — это записанное сужение периметра, не тишина.
6. Как проверяют: тест-команды из README.
7. Как выкатывают: `deploy/`, runbook продукта. Метод — `autoteam-release`, не хосты другого продукта.
8. Каденс ревью и документация: есть ли `docs/architecture/reviews/`, kb.
8а. Формат артефактов продукта: перед созданием артефакта в формате продукта прочитай соседние экземпляры того же типа (нумерация, статусы, обязательные разделы, точка входа). Формат, выведенный из README, но расходящийся с фактическими файлами, — дефект артефакта.
9. Верни карту: что канон продукта, что дыра, какой первый безопасный шаг.

Если в продукте нет короткой карты для следующих агентов — напиши `docs/process/agent-onboarding.md` в **этом** репозитории. Не жди просьбы.
