# Ретроспектива канона

Канон autoteam — baseline: во время работы над продуктом он неизменен. Улучшения проходят только через этот навык — предложениями, которые утверждает человек. Ты не правишь канон в рабочем цикле.

**Вход.** Журнал решений, брифы и handoff прогона, состояние цикла на финише и его история по чекпойнтам, места остановок, факты «скилл не сработал / не был найден / противоречил другому», и **наблюдения человека со стороны** (зависания, конфликты агентных сред, потери файлов) — цикл их не видит по определению, спроси явно. **Выход.** Отчёт ретро: что сработало, что стопало, предложения правок канона (добавить / изменить / убрать) с обоснованием фактами прогона. **Запреты.** Править канон самому; тащить в предложения детали проекта (имена, стек, домены, пути продукта) — правка формулируется обезличенно, как метод; предлагать новый skill по одному случаю. **Evidence.** Каждое предложение — ссылка на конкретный факт прогона (решение из журнала, остановка, расхождение). **Стоп.** Нет. Утверждение правок — человек. **Дальше.** Утверждено → правка канона отдельной задачей, затем разнос копий по проектам.

## Порядок

0. Ретро — задача **над траекторией**: читает журнал, handoff и чекпойнты — одного состояния не хватает по построению, потому что состояние намеренно держит только нужное следующей волне. Ради этого журнал и остаётся append-only.
1. Собери факты: где цикл встал и почему; что выпало из состояния и пришлось выяснять заново; где контекст волны рос вместо состояния (признак, что состояние ведут плохо); какие решения из журнала оказались неверными; какие скиллы не использовались или дублировали друг друга; где агент действовал «мимо канона» — и был прав.
2. Раздели: дефект метода (правило мешало) | дыра метода (правила не было) | дефект исполнения (правило было, агент не выполнил — это не повод менять канон).
3. Обезличь: из «в проекте X застряли на выборе БД» → «нет правила выбора хранилища при пустом входе». Тест: предложение читается без знания проекта.
4. Предложения: минимальный diff формулировкой «было → станет → почему»; на удаление — правило, которое ни разу не пригодилось за N циклов или систематически нарушалось без вреда.
5. Приоритет: сначала то, что останавливало цикл; потом качество результата; потом стиль.

Канал предложений: если канон — публичный репозиторий, среда умеет заводить issue и поручение/overlay это разрешает — каждое предложение отдельным issue в репозитории канона (формат «было → станет → почему», метка `retro-proposal`, без деталей проекта). Канала или разрешения нет — готовые тексты issue в очередь действий человека. Issue в публичном репозитории — публичное действие от имени человека: без явного разрешения не заводить. Issue — предложение, не правка: канон меняется только после утверждения человеком.

Каденс — по триггерам, не после каждого прогона (прогон без выводов — норма отлаженного процесса): первый прогон нового типа задачи; остановка или инцидент процесса; человек недоволен результатом; систематический ноль возвратов на приёмке; ~5 прогонов без ретро — лёгкий «пульс» (беглая сверка статистики: возвраты, замечания борда, время цикла — против деградации и стагнации).

Артефакт: `docs/process/retro-YYYY-MM-DD.md` в **продукте**; утверждённые правки — в канон отдельной задачей.
