# Документация: зачем, какая, когда обновлять

Это не «напиши README». Документация — часть поставки. Skill: `autoteam-docs`.

## Три слоя

| Слой | Кто читает | Где обычно | Запрещено |
|------|------------|------------|-----------|
| **Бизнес / продукт** | оператор, PM, заказчик | `docs/kb/`, раздел «Документация» в UI | внутренние пути репо, коды задач как меню |
| **Техническая** | разработчик, агент | `docs/`, ADR, runbook, OpenAPI | выдавать ADR за пользовательскую инструкцию |
| **Процесс** | команда и агенты | `docs/process/` | путать со spec продукта |

## Когда обновлять (каденс)

Обязательно в том же PR/задаче, если изменилось:

- наблюдаемое поведение экрана или API;
- роль, право, флаг;
- команда в админке;
- способ выкатки или отката;
- смысл требования (тогда и spec).

Регулярный проход (даже без фичи):

- активный продукт — раз в спринт / раз в 2 недели: устаревшие кнопки, расхождение UI и kb;
- спокойный — раз в месяц вместе с архитектурным ревью.

**Устаревшее:** кнопка, которой нет; обещание, которое код не делает; ссылка на удалённый экран; «так было в v1». Помечай и чини в той же волне, не копи документ «на потом» без владельца.

Владелец слоя документации — в README проекта. Нет владельца — оркестратор ставит обновление в очередь, не блокируя чужой код.

## Порядок в файлах

Файлы, растущие записями: свежее сверху. Проверка не на важность, а на обрезание — длинный файл читают частично (лимит чтения, grep, окно контекста), и режется хвост: со свежим внизу частичное чтение теряет текущую правду, со свежим сверху — историю, у которой есть другие дома (git, чекпойнты, ретро). Дискриминатор: можно ли прочитать запись №7, не читая №6? Тогда это лог — свежее сверху. Если порядок несёт смысл (шаги, разделы, зависимость: бриф, скоуп, спека, тело ADR, чек-лист, runbook), файл остаётся как написан. Реестры с ID держат порядок ID — там поиск важнее свежести, а время уже живёт в полях «срок годности» и «дата перепроверки». Лог объявляет свой порядок строкой под заголовком: иначе следующий пишущий допишет вниз, и файл станет со смешанным порядком, что хуже любой из двух конвенций.

Правится на месте или не переписывается — два разных класса, не смешивай. Реестр настоящего (пробелы, ресурсы, состояние) правится на месте: строка, переставшая быть правдой, заменяется, а её историю держит git. Лог не переписывается: отменённая запись получает амендмент. Не тащи амендментную бухгалтерию в реестр — строки «отменена такой-то» плодят там шум вместо картины того, что верно сейчас.

## Чего не делать

- Не описывать классы пакетов пользователю.
- Не выдумывать команды UI.
- Не держать единственную правду только в чате.
