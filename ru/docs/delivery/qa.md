# Проверки качества (QA)

TDD — сначала падающая проверка, потом код. Это не замена пирамиды. Выбирай проверки по изменённому поведению и его риску; мелкая правка текста/CSS не требует обхода всей системы. [Assurance](../process/assurance.md) ведёт более широкое покрытие и глубокие аудиты по рискам.

| Вид | Когда обязателен | Когда N/A |
|---|---|---|
| Unit | правила, расчёты, гонки в памяти | чистый макет CSS |
| Integration | БД, очередь, файлы | нет I/O |
| Contract | меняется API/событие между частями | внутренний рефактор без схемы |
| E2E | критичный пользовательский путь | правка копирайта |

Негативные случаи, права, идемпотентность — если есть деньги, ПДн, роли, повтор запроса. Для состояния/фоновой работы включай относящиеся к изменению случаи offline/reconnect, таймаута/зависания, частичного сбоя, перезапуска, владения worker/lease и прогресса. Если требование включает восстановление, проверяй его вместе с отказом.

Evidence: команда + вывод + код завершения, с ревизией, средой, данными/нагрузкой и временем, достаточными для воспроизведения. «В UI стало лучше» без запроса — не сдача для данных. Разделяй измеренный результат, вывод и неизвестное.

У каждой проверки различимы «ничего не произошло» и «всё хорошо»: скрипт-проверка assert'ит, что вообще сработала (подстановка состоялась, строка найдена); отчёт несёт exit code рядом с каждым выводом; ожидаемый непустой результат объявляется заранее — неожиданно пустой ответ это провал, не успех. Законно пустому/нулевому результату нужны заранее заявленное ожидание и evidence, что нужный запрос/проверка выполнились в нужной области.

Критерий приёмки выводится из способа сломаться, не из ожидаемого улучшения. Обязательный вопрос до формулировки: «как выглядит этот критерий, если правка сломана?» — совпадает с успехом → критерий негодный. Годные критерии различают состояния: «разброс значений существует», «ручка двигает результат» — а не «стало лучше».

Проверяй критерий и evidence общим протоколом: **утверждение → допущения → контрпример → контролируемая проверка → `CONFIRMED` / `REFUTED` / `INCONCLUSIVE`, с границами и следующим действием**. До проверки задай различающее наблюдение, ожидаемый результат, границы и условие остановки. Согласие агентов не доказывает правильность или спрос клиентов. Применяй протокол к брифу, находке, реализации, тесту и бизнес-гипотезе со свидетельствами, подходящими утверждению. Не превращай его в тяжёлый тест каждой строки исходника.

## Безопасные тестовые данные и побочные действия

Недостижимые на доступных данных состояния можно проверять временной модификацией **только в изолированной одноразовой/тестовой копии с отключёнными внешними действиями**. Изолируй учётные данные, workers, очереди, внешние вызовы, уведомления, платежи и других автоматических потребителей, чтобы копия не действовала на production или третьих лиц. Откат транзакции или восстановление строки не отменяет уже вызванные сообщение, платёж или действие worker.

Помечай evidence: исходный источник/снимок, что и как менялось, изоляция побочных действий, ожидаемый эффект, вывод и очистка/восстановление. Не выдавай синтетические/изменённые данные за наблюдение production. Немаркированная модификация данных в evidence запрещена. QA на production-данных требует отдельно разрешённой процедуры с последствиями, доступом, восстановлением и наблюдением; предположительно обратимое изменение строки не даёт достаточных полномочий.

## Спецификация и наблюдаемое поведение

Для существенного или спорного смысла проведи также независимую проверку первичных источников по [assurance](../process/assurance.md). Получи решающие ожидаемые наблюдения без копирования интерпретации автора. Согласованность спецификации, кода и созданных по ней тестов не выявит общую для них ошибку. Закрепи исходную проблему и сравнивай фактическое продвижение между возвратами; смена модели не обнуляет неудачные подходы.

Суждение о правильности логики без сверки со спецификацией домена (если она существует) — суждение о согласованности кода с самим собой, не о правильности. Расхождение кода со спецификацией — находка в обе стороны: может врать код, может устареть спецификация; фиксируются оба варианта. Практика: построчный реестр сверки «спецификация ↔ код» (совпадает / расходится / не реализовано) — после него «в коде так» перестаёт быть аргументом. Такая сверка не требует отдельного тяжёлого теста на каждую строку.

Настройки: «читается» ≠ «работает». Проверка настройки — сквозной путь «изменил → увидел другой результат на наблюдаемом выходе, за известное время», включая уже посчитанное (см. производные данные в [data.md](data.md)). Настройка без наблюдаемого эффекта — мёртвая, это находка.

Находка класса «потеря или порча данных»: чтения кода недостаточно — либо безопасное воспроизведение, либо явная пометка «механизм подтверждён, масштаб не измерен» и требуемый разрешённый прогон в очередь с владельцем. Неудача воспроизведения — свидетельство в своих границах, а не доказательство невозможности механизма.

## Проверяй проверки

Тест проверяется мутацией: сломай проверяемое поведение на изолированной копии — тест обязан упасть. Всегда проходящий тест — дефект. Выбирай мутации на значимой границе поведения/инварианте, а не механически на каждой строке; сохрани мутацию и падающий вывод как evidence, затем восстанови правильную реализацию.

Прогресс-инварианты (курсор, граница, окно, обязанные двигаться) проверяются последовательностью шагов с требованием движения на каждом — одиночная проверка «в допустимых границах» пропускает «застрял». Для асинхронной работы задай наблюдаемый срок завершения и при необходимости проверь владение/восстановление; «worker жив» само по себе не доказывает прогресс. Структурное свойство, не выражающееся в поведении (например, разбиение сборки), законно проверяется чтением исходника — с записанным обоснованием, почему поведением проверить нельзя.

Храни находки со стабильными ID в [системе рабочих элементов](../process/work-items.md), устраняй дубли наблюдений, связывай исправления с независимой проверкой, а принятые повторно применимые уроки — со [знаниями проекта](../process/project-knowledge.md). Зелёные проверки не закрывают непроверенные направления и не принимают остаточный риск молча.

Skill поставки: `autoteam-delivery`. Гонки: `autoteam-quality`. Широкие аудиты: `autoteam-audit`.
